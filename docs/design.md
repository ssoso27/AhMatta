# AhMatta 설계 초안

작성: 2026-09-18 · 상태: 사용자 제품 흐름 검토 완료, 구현 전

화면 가독성·점진적 수정 기준은 [화면 기준](ui-design.md)에서 관리한다. 시각 기본값은 실제 화면으로 확인하기 전까지 제안이다.

## 목적

새 요청 때문에 중단한 일을 잊지 않고 다시 시작한다. 사용자는 작업 전환 때 버튼을 한 번 누르고, 앱은 중단 목록과 날짜별 작업 기록을 만든다.

성공 기준은 다음 네 질문에 바로 답하는 것이다.
- 지금 뭐 하고 있었지?
- 하다 만 일이 뭐였지?
- 누구에게 답하거나 무엇을 처리해야 하지?
- 어제 어떤 작업을 얼마나 했지?

개인 1인용으로 시작한다. 사용자가 답을 늦게 해도 바꿀 수 있는 세부사항은 기본값으로 설계한다. 새 비용, 회사 Slack 접근 권한, 서버 접속 정보는 확인이 필요한 외부 조건이다.

## 사용자에게 확인된 요구

- 웹과 macOS 데스크톱에서 사용. Electron 선호, Windows는 나중에 고려.
- 작고 세로로 긴 창, 크기 조절과 복원, 반응형 화면, 글자 확대.
- 제목, 요청자, 원문 링크, 수동 작업 전환 기록.
- 날짜별 간트차트와 간단한 작업 목록.
- Slack은 DM, 직접 멘션, 지정한 채널의 요청까지 포함.
- Slack 수집은 5분 간격. 앱이 닫혀 있어도 홈서버에서 수집.
- 개인 홈서버: Raspberry Pi 4. 사용자 최초 메모는 2 CPU / RAM 4 GB / HDD 64 GB. SSH 실측은 아래 배포 환경에 반영한다.
- LLM이 필요하면 개인 ChatGPT Plus 계정을 우선 검토. 회사 Codex 계정과 분리.

## 접근 방식 비교

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 공통 웹 화면 + 얇은 Electron 앱 + 홈서버 | 데스크톱과 웹을 함께 유지하며 상시 수집 가능 | 서버 연결과 로그인 필요 | 추천 |
| 웹만 먼저 제공 | 구현·배포가 가장 단순 | 창 복원, 트레이 등 데스크톱 경험 제한 | 공통 화면 개발의 첫 단계 |
| 데스크톱 로컬 우선 + 서버 동기화 | 오프라인에서 강함 | DB 복제·충돌 해결이 초기 범위를 키움 | 추후 필요할 때 |

웹 화면과 핵심 기능을 먼저 완성하고 같은 화면을 Electron으로 감싼다. 데스크톱 UX가 맞지 않으면 같은 데이터로 웹을 계속 사용한다.

## 핵심 사용 흐름

### A → B → C → A

1. A에서 시작을 누르면 A의 작업 구간이 열린다.
2. B에서 시작을 누르면 같은 시각에 A 구간을 닫고 B 구간을 연다. A는 하다 만 작업에 남는다.
3. C로 전환해도 A와 B는 유지된다.
4. C를 완료하면 직전에 하던 B를 재개 후보로 보여준다. 자동으로 타이머를 시작하지 않는다.
5. A를 재개하면 A의 새 구간이 생긴다. 기존 구간과 합산하되 간트에는 각각 표시한다.

전환할 때 메모는 선택이다. 입력창이나 확인창이 전환을 막지 않는다. 작업 카드에서 나중에 이어 할 한 줄을 적을 수 있다.

빠른 등록은 제목만 필수다. 요청자, 링크, 마감, 메모는 나중에 넣을 수 있다. 수동 생성 시 '추가'와 '추가하고 시작'을 제공한다.

### 요청과 답장

답장 여부와 작업 완료 여부를 별도로 관리한다.

- 수집된 요청은 답할 요청에 들어간다. 질문인지 확실하지 않은 항목도 확인 가능하게 남긴다.
- 같은 스레드에 내 답장이 발견되면 답장 표시를 하고 할 일로 이동한다. 아직 할 일인지 확정되지 않았음을 표시한다.
- 단순 답변으로 끝난 항목은 끝남 버튼으로 정리한다.
- '확인해 볼게요'처럼 후속 행동이 필요한 답장은 할 일에 남는다.
- 이미 작업과 연결된 스레드는 같은 작업을 갱신한다. 같은 스레드에 별도 요청이 있으면 수동으로 작업을 나눌 수 있다.
- 일반 DM에서 서로 다른 주제가 섞여 답장의 대응 관계가 애매하면 자동 이동하지 않고 답장 확인이 필요하다고 표시한다.
- 새 후속 질문은 답장 필요 상태를 다시 켤 수 있지만, 완료 작업을 자동 재개하지 않는다.
- 답하기 전에 바로 작업을 시작할 수도 있다. 답장 상태는 그대로 남는다.

Slack으로 답장을 보내는 기능은 첫 버전에 넣지 않는다. 원문 열기로 Slack에서 답한다.

## 화면

첫 창 크기 제안은 400 × 760 px. 폭 360 px에서도 핵심 버튼과 제목을 사용할 수 있게 한다. 확대 상태에서는 세로 스크롤을 허용한다.

하단 메뉴는 지금 / 기록 / 설정이다.

### 지금

상단에는 빠른 추가와 현재 작업, 경과 시간, 일시정지·완료 버튼을 둔다.
그 아래는 하다 만 작업, 답할 요청, 아직 시작하지 않은 할 일 순서다. 각 묶음에 개수와 접기를 제공한다.

작업 카드는 제목, 요청자, 상태, 마지막 작업 시각, 이어 할 메모를 보여준다. 원문 링크 버튼은 Slack 또는 해당 URL을 연다. 카드 본문은 상세 내용을 펼치며 시작 버튼과 링크 클릭 영역을 구분한다.

하다 만 작업은 최근 중단 순서가 기본이다. 별도로 '어제부터 남은 일'을 표시해 새 요청 아래에 오래된 작업이 계속 묻히지 않게 한다. 상대 답변 대기에는 다시 확인할 날짜를 둘 수 있다.

작업마다 일정한 색을 사용해 목록과 간트에서 같은 일을 찾게 한다. 상태는 색뿐 아니라 글자로 표시한다. 현재 작업을 가장 강하게 강조한다.

데스크톱은 창 크기·위치·확대 비율을 저장한다. 화면 밖으로 나간 위치는 복구한다. Cmd +/-/0을 제공하고 웹에서는 브라우저 확대를 따른다. 항상 위에 표시는 선택 설정이다.

### 기록

날짜를 선택하면 작업별 실제 수행 구간을 간트차트로 보여준다. 하루 전체 작업 목록과 작업별 합계, 완료 여부도 함께 표시한다.

- 좁은 창: 시간축만 가로 스크롤하고 작업명은 고정한다.
- 넓은 창: 목록과 간트를 나란히 보여준다.
- 같은 작업을 여러 번 재개하면 같은 행에 여러 막대가 생긴다.
- 자정을 넘긴 구간은 날짜별 합계를 나눠 계산한다.
- 기록이 없는 시간은 빈 구간으로 남긴다.
- 구간의 시작·종료 시각 수정과 누락 구간 수동 추가를 제공한다. 중복 시간은 저장 전에 알려준다.
- '어제 한 일 복사'는 실제 기록만으로 작업명·시간·완료/진행 상태를 만든다. 자동 발송은 하지 않는다.

첫 버전의 간트는 실적 기록이다. 미래 일정 배치, 작업 의존성, 예상 종료일 계산은 다음 범위로 둔다.

## 상태와 데이터

작업 상태는 할 일 / 진행 중 / 중단 / 상대 답변 대기 / 완료 / 취소로 구분한다. 다시 확인할 날짜가 있는 작업은 해당 날짜에 목록 상단으로 올린다. 완료하지 않은 항목은 날짜가 바뀌어도 유지한다.

| 데이터 | 역할과 주요 값 |
|---|---|
| Task | 제목, 상태, 요청자, 색상, 메모, 마감, 다시 확인할 날짜, 변경 버전 |
| WorkSession | 작업 ID, 시작·종료 시각, 기록 장치, 수정 여부 |
| InboxItem | 요청 후보, 답장 상태, 판별 근거, 연결된 작업 |
| SourceMessage | 워크스페이스·채널·메시지 ts·thread ts·발신자·본문 일부·원문 링크 |
| TaskSource | 여러 원문과 작업 연결. 요청 중복 병합과 작업 분리 지원 |
| SyncCheckpoint | 수집 대상, 마지막 성공 구간, 페이지 진행 상태, 오류 |
| Preferences | 시간대, 표시 설정, 지정 채널, 알림 설정 |

서버가 한 사용자의 진행 중 작업 구간을 최대 하나로 제한한다. 전환은 기존 구간 닫기와 새 구간 열기를 한 트랜잭션으로 처리한다. 중복 클릭·재시도는 요청 ID로 중복 실행을 막는다. 웹과 앱에서 동시에 전환하면 오래된 변경을 거부하고 현재 작업을 새로 표시한다.

시각은 UTC로 저장하고 기본 표시 시간대는 Asia/Seoul이다. 직접 수정한 기록은 수정 전 값과 함께 보존한다.

## 기술 구성 제안

- 공통 UI: React + TypeScript + Vite.
- 데스크톱: Electron. 창 관리, 확대, 트레이, 선택적 알림만 담당.
- API: Python FastAPI, 단일 API 프로세스. 로컬 개발은 프로젝트 .venv, 서버는 전용 컨테이너로 격리.
- 저장소: 서버 로컬 디스크의 SQLite. 작업 기록·요청 후보·동기화 상태 저장.
- 수집 작업: 같은 Python 코드의 별도 worker 컨테이너가 5분마다 실행. 실행이 늦어져도 겹치지 않게 하고 완료된 지점부터 이어간다.
- 브라우저는 API에서 현재 상태를 주기적으로 다시 읽고, 탭에 돌아올 때 즉시 갱신한다.

서버 경로는 /home/ssoso27/workspace/ahmatta를 제안한다. Docker Compose 프로젝트 이름은 ahmatta, 서비스는 api와 worker로 나눈다. 둘은 서버 로컬의 전용 데이터 디렉터리를 공유하고 SQLite 쓰기 트랜잭션은 짧게 유지한다. 컨테이너별 DB 복사본을 만들지 않는다.

API의 호스트 포트 후보는 127.0.0.1:18741이다. 조사 시 사용되지 않았지만 배포 직전에 재확인한다. 정적 웹 빌드는 맥에서 하고 API가 결과물을 제공한다. 서버에 Node를 설치할 필요가 없다. 서버 컨테이너는 ARM64 런타임으로 고정하고, Python 버전과 의존성은 구현 시 함께 고정한다.

기존 nginx·방화벽·다른 컨테이너의 설정을 수정하지 않고 먼저 SSH 터널로 접속을 검증한다. 상시 웹 접근은 기존 Tailscale 환경을 활용하는 방향으로 잡되 접근 경로를 배포 단계에서 확인한다. 컨테이너 재시작 정책, CPU·메모리 상한, 로그 회전, SELinux에 맞는 전용 볼륨 권한을 설정한다. 기존 공유 디렉터리 전체의 권한이나 SELinux 레이블을 바꾸지 않는다.

### 2026-09-18 서버 읽기 전용 확인 결과

- 접속: ssh dongtan-server. 사용자 ssoso27.
- Rocky Linux 9.7 / aarch64 / 온라인 CPU 4개.
- RAM 3,794 MiB, 확인 시 available 3,362 MiB. swap 없음.
- 루트 파일시스템 117 GB, 여유 111 GB. 저장장치 종류는 확인하지 않음.
- /home/ssoso27/workspace에 hamsters, joonsik-planner가 있음. ahmatta는 없음.
- nginx, Docker, Tailscale, firewalld 실행 중. 기존 웹 포트 80·18080 사용 중.
- 기존 Docker 컨테이너 2개 실행 중.
- 시스템 Python 3.9.25. SSH 세션 PATH에 Node·uv가 없음.
- 사용자 systemd linger 비활성, SELinux Enforcing.
- SSH 조회만 수행. 파일 생성, 패키지 설치, 서비스·계정 변경 없음.

이 결과에 따라 초기 systemd timer + 서버 venv 제안은 전용 Docker Compose로 변경한다. Compose 플러그인 사용 가능 여부와 이미지 ARM64 지원은 배포 전에 확인한다.

1인용 인증을 두고 HTTPS 또는 기존 사설망을 통해 접속한다. Slack 비밀정보는 서버에만 둔다. Electron 화면에는 Node 권한을 주지 않고 필요한 기능만 제한된 통로로 노출한다. 외부 링크는 허용한 URL 형식만 시스템 브라우저로 연다.

첫 버전은 서버 연결을 전제로 한다. 연결이 끊기면 마지막 목록과 연결 끊김 표시를 제공하며, 서버 저장이 실패한 전환을 성공으로 보여주지 않는다. 입력 중인 빠른 등록 내용은 로컬에 보관한다. 완전한 오프라인 작업·동기화는 후속 기능이다.

## Slack 수집

사용자가 선택한 채널, DM, 접근 가능한 대화의 직접 멘션을 대상으로 한다. 개인 DM을 읽을 권한이 있는 정식 사용자 인증이 필요하며 일반 봇 토큰만으로 모두 읽을 수 있다고 가정하지 않는다.

5분은 수집 시작 간격이다. 모든 요청이 반드시 5분 이내 들어온다는 보장은 하지 않는다. 페이지 처리량, Slack 제한, 장애에 따라 지연될 수 있어 마지막 성공 시각과 지연 상태를 화면에 표시한다.

수집은 마지막 성공 지점보다 조금 앞에서 다시 시작하고 메시지 식별자로 중복을 제거한다. 모든 페이지의 저장이 끝난 구간까지만 체크포인트를 전진시킨다. 실패 시 다음 실행에서 이어받고 API 제한은 Retry-After를 따른다.

채널 본문 조회만으로 오래된 스레드에 달린 새 답장을 모두 찾을 수 있다고 가정하지 않는다. 실제 워크스페이스의 검색·스레드 조회 권한으로 다음을 사전 검증한 뒤 수집 방법을 확정한다.
- 오래된 스레드에 새로 달린 직접 멘션과 요청을 발견하는가?
- 추적 중인 요청의 내 답장을 발견하는가?
- 개인 DM, 그룹 DM, 지정 채널별 접근 범위가 맞는가?
- 대상 대화 수를 5분 주기 내에 처리할 수 있는가?

미지원 범위는 화면에서 명시하고 링크 붙여넣기로 수동 등록할 수 있게 한다. Slack 연동이 준비되지 않아도 핵심 작업 관리 개발은 진행한다.

## AI

첫 버전의 기록·전환·복귀·보고서에는 AI가 필요 없다. 채널 요청 판별과 제목 요약을 보조하는 교체 가능한 모듈로 둔다.

DM과 직접 멘션은 우선 후보로 남긴다. 지정 채널은 요청 표현과 대상자 규칙으로 후보를 만들고 나머지 수집 메시지도 최근 수집함에서 확인할 수 있게 한다. AI를 붙여도 불확실한 메시지는 확인 필요로 남긴다. 자동 완료와 영구 삭제를 AI 판단에 맡기지 않는다.

개인 ChatGPT 로그인은 Codex App Server의 공식 인증 경로를 이용하는 방안을 우선 검증한다. 회사 계정의 인증·설정과 분리한다. 일반 OpenAI API는 별도 과금이므로 자동 전환하지 않는다.

개인 Plus 계정의 이용 가능 상태, 사용량 제한, 홈서버 Linux ARM 환경 실행 여부와 분류 지연은 아직 검증하지 않았다. 실패하거나 한도에 닿으면 AI만 일시 중단하고 요청 후보는 계속 수집한다.

분류기는 필요한 메시지 문맥만 받고 구조화한 결과만 반환한다. 파일·명령 실행 권한을 주지 않는다. 회사 메시지를 개인 서버와 개인 AI 계정으로 처리할 수 있는 범위는 실제 연동 전에 확인한다.

## 기록을 믿을 수 있게 하는 예외 처리

- 명시적 휴식·업무 종료는 현재 구간을 닫는다.
- Electron에서는 절전 시 구간 종료를 시도한다. 실패하거나 비정상 종료한 경우 마지막 활동 신호를 근거로 다음 실행에서 종료 시각 수정을 제안한다.
- 웹에서는 장시간 무활동이나 연결 단절을 실제 업무 종료로 단정하지 않는다. 비정상적으로 긴 구간을 확인 대상으로 표시한다.
- 수정하지 않은 의심 구간은 보고서에도 미확인으로 표시한다.
- 앱 재시작은 서버의 현재 작업을 복구한다.
- SQLite 온라인 백업 기능으로 일별 백업을 만들고 복원 절차를 검증한다. 같은 디스크의 백업만으로 디스크 고장에 대비했다고 보지 않으며 별도 보관 위치는 배포 때 정한다.
- 원문은 필요한 텍스트와 링크 위주로 저장하고 첨부파일은 다운로드하지 않는다. 보관 기간과 로그 용량에 상한을 둔다.

## 구현 순서와 완료 기준

1. 핵심 웹: 빠른 등록, 전환, 중단 목록, 재개, 완료, 기록 간트·목록, 어제 한 일 복사.
   - A→B→C 후 다음날 A·B가 남고, 재개한 A의 시간은 기존 구간과 정확히 합산되어야 한다.
2. Electron: 공통 화면, 창·확대 복원, 원문 링크, 절전·재시작 처리.
   - 작은 창과 확대 화면에서 주요 버튼이 가려지지 않아야 한다.
3. Slack: 인증과 수집 범위 검증, 5분 수집, 요청 후보, 답장 표시, 작업 연결.
   - 재수집·중간 실패에도 중복과 누락 없이 복구되는지 검증한다. '확인할게요' 답장이 완료로 처리되지 않아야 한다.
4. 선택적 AI: 요청 판별·제목 요약, 개인 계정 연결 검증.
   - 오판을 고칠 수 있어야 하고 AI 장애가 작업 관리나 Slack 원문 수집을 멈추지 않아야 한다.

단계 1의 일상 사용 가능 상태를 첫 목표로 삼는다. 이후 실제 사용에서 전환 버튼을 놓치는 상황과 요청함 잡음을 관찰해 개선한다. Slack 연동 권한 검증은 단계 1 설계가 정해지면 일찍 수행한다.

## 아직 확인할 외부 조건

- 지정할 Slack 채널과 앱 설치·사용자 인증 가능 여부.
- 회사 메시지의 개인 서버·AI 처리 가능 범위.
- 홈서버 접속·아키텍처 확인 완료. 상시 웹 접근 경로, Compose 플러그인과 컨테이너 런타임 버전은 배포 때 확정.
- 개인 ChatGPT 로그인 기반 Codex 연동의 실제 실행과 한도.

이 조건들은 해당 연동·배포 단계의 조건이다. UI와 작업 기록 설계를 막지 않는다. 자동화 예약, 실제 서버 변경, 계정 연결은 아직 수행하지 않았다.
